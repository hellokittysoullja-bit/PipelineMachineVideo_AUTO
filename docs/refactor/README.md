# Перестройка отбора кадра: этапы и доказательства

План — единое ядро отбора для фото и видео, одна точка, где решение о
кадре становится состоянием эпизода, объектив вместо лексикографии, ниша
вне кода. Правка такого размера безопасна ровно настолько, насколько можно
показать, что новый код выбирает тех же победителей там, где обязан, и
отличается только там, где исправлен названный дефект. Поэтому первым
построен инструмент доказательства, и каждый этап принимается им.

## Этап 0 — харнесс эквивалентности (`scripts/selection_freeze.py`)

`record` запускает НАСТОЯЩИЙ `main()` в режиме `--select-only` (весь отбор,
ни одного клипа рендера) и записывает всю сеть (`scripts/net_recorder.py`);
`verify` воспроизводит прогон без сети и сравнивает по слотам.

Герметичность — список закрытых источников расхождения, каждый найден на
практике:

| источник | как закрыт |
|---|---|
| сеть | 100% вызовов через `urllib.request.urlopen`, перехват на границе процесса; последовательность ответов по каждому адресу (429, затем 200) |
| дисковые кэши поиска | у каждого прогона свои пустые (в реальном отчёте эпизода 94 музейный поиск целиком пришёл из прогретого кэша) |
| окружение | переменные выводятся из кода; `.env` дочерний процесс не читает; секреты — отпечатками |
| соль хэша, веса моделей | `PYTHONHASHSEED` записан; `HF_HUB_OFFLINE` |
| **часы** | остывание Мет после 403 — функция настенного времени, и карточки тянутся параллельно; решение «в остывании?» записывается с привязкой к запросу и воспроизводится (`scripts/time_decisions.py`). Найдено замером: запись эпизода 93 кодом этапа 0, воспроизведение тем же кодом — один запрос к Мет пропал, другой появился |
| правка кода во время прогона | модуль исполняется из снимка исходника, снятого один раз; тот же снимок регистрируется в `linecache` (подписи кэша строятся `inspect.getsource`). Найдено на себе: якоря покрытия посчитались по версии файла, которую я правил, пока шла получасовая запись |

Харнесс судит и чужую ревизию (`--pipeline`, например из `git worktree`):
база снимается кодом предыдущего этапа, новый код сравнивается с ней.

### Как харнесс решает, законно ли расхождение

Слот получает ровно один класс:

- **СОВПАЛ**;
- **ОЖИДАЕМО РАЗОШЁЛСЯ** — автор назвал слот исправлением ДО прогона, и он
  изменился; **НЕОЖИДАННО СОВПАЛ** — назвал, а он не изменился (провал:
  правка не сработала или предсказание неверно);
- **ВХОД ИЗМЕНИЛСЯ** — общее состояние на начало слота (анти-дубль, ритм,
  история видов медиа, яркость, перенос длительности) у прогонов разное;
  харнесс снимает его сам в начале каждой итерации цикла и называет поля;
- **УТЕЧКА УСТРАНЕНА** — вход тот же, но журнал нового прогона показывает в
  этом слоте утечку старой семантики (у отброшенной попытки были резервы
  или вердикты, которые старый код применял);
- **РАЗОШЁЛСЯ** — никакой причины нет: провал.

Сеть судится парами «адрес × слот», а не адресом целиком: общий адрес
(превью, поиск по запросу секции) звучит во многих слотах, и лишнее
обращение в слоте с причиной не делает необъяснёнными слоты, где число
обращений совпало. Решения по часам (остывание Мет) тоже помечены слотом и
вне записи законны только в слоте с причиной. Сводный отчёт источников по
слотам не раскладывается, поэтому судится проверкой, а не разрешением:
законен, только если сменились слоты с причиной И побед у каждого
источника ровно столько, сколько его кадров на экране. Все три правила
найдены на эпизоде 93, где харнесс первой версии поднял ложную тревогу:
ни одно из расхождений не было настоящим.

Ручного «ниже по течению» нет: слот с тем же входом и без собственной
утечки обязан совпасть бит-в-бит. Отчёты с записями по слотам вправе
расходиться только в записях слотов с причиной; прочие отчёты, код возврата
— только если названы заранее. Сеть: каждое обращение помечено слотом
(трассировщик читает `i` слотового цикла), и расхождение сети допустимо
только в слотах с причиной. Запрос, которого нет в записи (новый код
законно выбрал другой кадр), с `--live-fallback` выполняется живьём в
отдельный слой и остаётся названным.

## Этап 1 — одна точка, где решение становится состоянием

`scripts/selection_attempt.py`: добытчик работает внутри попытки и ничего
не меняет сам — вердикты, резервы анти-дубля, ритм, победа источника,
строка лицензионного манифеста записываются в попытку, файл кадра пишется в
её приватный стейджинг. `close_slot()` в `pipeline_smart.py` — единственное
место, где одна попытка принимается (эффекты применяются, файлы переезжают
в кэш), остальные закрываются отказом, а в отчёты слота идут вердикты той
попытки, по которой принято решение. `_slot_miss_snapshot`/`_restore`
удалены вместе с понятием «вердикты номера слота».

Закрытые дефекты (все одного класса — «состояние меняется до решения»):

1. вердикт отвергнутого видео поглощал найденное фото;
2. видео, заменённое фотографией, занимало анти-дубль следующих слотов;
3. поздняя карточка оставляла резервы отвергнутого кадра;
4. выброшенный кадр лежал в кэше и на следующем прогоне воскресал
   кэш-хитом без вердиктов;
5. лицензионный манифест получал строки кадров, не попавших на экран;
6. запасной видео-ярус не засчитывал победу источнику;
7. шотлист при поздней карточке фиксировал выброшенный кадр.

Инварианты проверяются по AST (`tests/test_selection_attempt.py`): вне
`apply_selection_effect` нет ни одной мутации анти-дубля/ритма/истории, вне
проекции — ни одной записи в отчёты промахов; победа источника и
лицензионный журнал — только через применитель; коммит и отказ — только в
`close_slot`. Контроль: на коде до этапа те же проверки находят 21 мутацию
состояния и 11 записей в отчёты в обход решения.

### Приёмка на эпизоде 94

Ожидания зафиксированы до прогона (`stage1_expect_94.json`). Результат —
ЭКВИВАЛЕНТНО:

- слот 4 изменился, как предсказано: кадр 38104230 на экране вместо
  поглощения;
- слот 5 — сменилось только имя клипа; харнесс назвал причину сам:
  изменились перенос длительности, яркость, история видов медиа,
  анти-дубль;
- слоты 2 и 3 (видео заменено фото) — журнал показывает устранённую
  утечку, исход тот же;
- сеть: единственный запрос вне записи — в слоте 4.

**Ошибка предсказания, найденная харнессом.** В первой версии ожиданий
стояло, что изменится `source_contribution.json`. Не изменился: старый код
засчитывал победу найденному фото слота 4 в момент добычи, ещё до
поглощения, а видео, заменённые фото в этом эпизоде, были запасными,
которым `won` не начисляли и раньше. Итог совпал. Ожидание исправлено, а
не подогнано: харнесс ровно для того и требует назвать причину заранее.

Остальные эпизоды — в `stage1_results.md` по мере прогона.

## Этап 2 — один запрос на слот и ядро отбора

`scripts/selection_engine.py`: `SlotRequest` (неизменяемый, без значений по
умолчанию) и `select(request, adapter)`. Запрос строится в одном месте
(`build_slot_request`) один раз на слот и передаётся всем попыткам слота,
включая спасение фотографией после негодного видео. Раньше каждая попытка
перечисляла аргументы заново, и спасающий вызов годами шёл без брифа фразы
(в эпизоде 94 так искались 5 слотов из 8) — теперь это невозможно по
построению: другого запроса у попытки нет.

Ядро делает то, что общее для любого вида медиа: путь в кэше и кэш-хит (что
годно на кэш-хите, решает адаптер), перевод пути в стейджинг попытки, сборку
пула (бриф фразы первым, затем запрос слота и секции; кандидаты источников по
кругу внутри запроса, запросы по кругу; дубль по id — при первом появлении;
жанровый фильтр; счёт «предложено»). В ядре нет ни ветки по виду медиа, ни
импорта `pipeline_smart` или адаптеров (проверяется по AST). Отбор фото —
`PhotoAdapter`: его методы — дословно тело прежнего `pexels_photo`, разрезанное
по фазам. Видео переходит на ядро на этапе 3.

Пустой после жанрового фильтра пул теперь честное «кандидатов нет». Раньше
фото-путь падал на `candidates[0]` (IndexError), и исключение засчитывалось
как сбой API Pexels — шаг к отключению стока на весь эпизод из-за того, что
все кандидаты оказались не по жанру.

Харнесс к этапу 2 научился:

- снимать **вход каждой попытки** — поля запроса слота в момент вызова отбора
  (у кода этапа 1 — аргументы добытчиков под теми же именами) — и принимать
  его как причину расхождения («ЗАПРОС ПОПЫТКИ ИЗМЕНИЛСЯ»), **только если
  изменившиеся поля объявлены этапом заранее** (`attempt_fields`).
  Необъявленное изменение запроса причиной не считается, иначе ошибка
  передачи запроса объясняла бы сама себя;
- воспроизводить и запись, и живые ответы другого прогона
  (`--net-overlay-from`), чтобы этап сравнивался с предыдущим этапом бит в бит,
  включая то, что предыдущий этап скачал живьём;
- узнавать ветви в методах класса (`PhotoAdapter.choose`).

Id попыток стали местными для слота: сквозной счётчик процесса сдвигал id во
всех последующих слотах, стоило одному слоту сделать на попытку больше.

### Приёмка этапа 2 на эпизоде 94

База — прогон кода этапа 1 новым харнессом (`s1`, ЭКВИВАЛЕНТНО против
записи). Этап 2 против неё (`s2b`) — ЭКВИВАЛЕНТНО: слоты 1, 4, 7, 8
совпали бит в бит; 2, 3, 5 — «запрос попытки изменился» ровно по
объявленным полям (бриф и текст фразы дошли до спасающей фото-попытки);
6 и 9 — изменившийся вход. Первая попытка (`s2`) упала на решениях по
часам без слота — это был не код этапа, а мой перенос правки харнесса:
`git apply` применяет всё или ничего, и файл записи часов в рабочую копию
не доехал, хотя напечатал «applied cleanly». Найдено разбором, исправлено,
перепроверено.
