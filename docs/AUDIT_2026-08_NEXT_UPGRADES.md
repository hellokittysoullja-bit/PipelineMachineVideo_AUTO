# Аудит генератора (08.2026): что исправлено и что можно апгрейдить дальше

Записано по итогам полного разбора кода (`scripts/*.py`, 13.9k строк). Формат
тот же, что у `ROADMAP_CINEMATIC_UPGRADES.md`: сначала факт, потом цена.

Всё, что перечислено в разделе «Апгрейды», — **только код**: без денег, без
квоты, без ручного труда, если цена не написана явно. Ни один пункт не
требует компромисса по качеству картинки/звука — это либо закрытие
интеграционного пробела, либо перенос уже проверенного решения из одного
файла в другой, либо чистое ускорение без изменения результата.

## ЧАСТЬ 1. Уже исправлено в этой сессии (для истории)

Порядок — по цене ошибки, не по размеру правки.

1. **Падение всего прогона на любом блоке без медиа.** Проверка порядка
   заданий требовала `job["i"] == позиция_в_списке`, а блок без медиа
   (кончилась квота Pexels, пустая выдача, нет ключа) в список штатно не
   попадает. После первого же такого блока рендер падал сырым
   `AssertionError` вместо отчёта `RENDER_STRICT_GATE`. →
   `check_jobs_in_order()`.

2. **Накопительный рассинхрон картинки с голосом (десятки секунд).** Тип и
   длительность перехода выбирались по хэшу путей клипов, а пути зависят от
   длительностей, которые считаются из бюджета переходов — круговая
   зависимость, из-за которой бюджет брался «сверху» (0.167с) вместо факта
   (85% склеек — один кадр). На синтетическом 40-минутном эпизоде (464
   блока) видео выходило на **25.4с длиннее аудио**: хвост обрезался
   финальным муксом, картинка к концу отставала от текста. →
   `plan_transitions()` + точный `estimate_xfade_budget()`; расхождение
   бюджета с фактом теперь 0.0000с.

3. **+20мс на каждый клип в одну сторону** (ffmpeg отдавал 86 кадров = 3.583с
   там, где заказано 3.567с) — ~9с систематического ухода на эпизод. →
   кадровая сетка `quantize_durations_to_frames()` с диффузией ошибки
   округления + заказ клипа в кадрах (`-frames:v`) вместо секунд (`-t`).

4. **Вторая копия CLIP-модели в памяти (~+600МБ).** `pipeline_smart` живёт как
   `__main__`, и голый `import pipeline_smart` из `look_reference`/
   `visual_director` исполнял файл второй раз, с отдельным набором глобалов
   (включая кэш модели). При том что число рендер-воркеров считается как раз
   по свободной памяти.

5. **Ролик из нескольких картинок по кругу.** `use_local` взводится от ОДНОГО
   фото в `media/`, а выдача шла по кругу — штатный Шаг 5 протокола
   (AI-картинки под хук, остальное стоком) давал эпизод из этих нескольких
   картинок, повторённых десятки раз, без единого обращения к Pexels.

6. **Одна и та же сток-фотография на десятки слотов.** Все источники в
   `stock_fetch_multisource.py` брали жёстко первый результат выдачи, а
   запрос приходит из тематического словаря по корню слова — десятки слотов
   получают один запрос, значит и одну картинку.

7. **`assemble.py` собирал ролик из сырого `audio.mp3`** (искал
   `audio_fixed.mp3`, а `fix_pauses.py` давно отдаёт `.flac`) — то есть без
   подрезки пауз и нормализации громкости даже после честного Шага 7. Там же:
   лишние секунды видео без звука в хвосте (`-shortest` при `-c:v copy` без
   `-t`), перебор бюджета склейки на 39с, приём слишком длинных клипов из
   кэша, отсутствие проверки на застревание ffmpeg.

8. **Неграмотная озвучка на основном контенте канала.** «1 кг» →
   «1 килограммов», «1,5 кг» → «1,5 килограммов» (форма единицы не
   согласовывалась с числом). Баг платный: текст уходил в TTS.

9. **ffmpeg вообще не запускался на длинных роликах** (Windows): граф
   фильтров `fix_pauses.py` растёт пропорционально числу пауз и упирался в
   лимит длины командной строки 32767 символов. → `-filter_complex_script`.

10. Мелкое: обрезанные файлы после обрыва скачивания (атомарная запись),
    хвостовая тишина без закрывающей метки `silence_end`, `os.listdir` по
    несуществующей папке эпизода на импорте, относительный путь в
    `render_with_retry.py`, 11 красных тестов на чистой установке
    (опциональный `ruaccent`), нечитаемые `\uXXXX` в комментариях.

**Тесты:** +40 регрессионных, вся сюита зелёная (421 passed).
**Не проверено вживую:** в окружении аудита нет ffmpeg, поэтому 152 теста,
которым он нужен (включая дымовой прогон полной сборки), пропущены. Правки
командных строк ffmpeg (`-frames:v`, `-filter_complex_script`, `-t`)
проверены по документации и логике, но первый реальный рендер эпизода —
обязательный шаг приёмки (Шаг 7.5 протокола).

## ЧАСТЬ 2. Апгрейды без компромиссов

### 2.1. Локальные сток-ВИДЕО из `media/` не используются вообще

**Факт.** `stock_fetch_multisource.py` по схеме ЧАСТИ 14 качает на чётные
слоты видео (`NNN_stock_video.mp4`), а `pipeline_smart.py` умеет брать из
`media/` только фото (`local_photo()` фильтрует `.jpg/.jpeg/.png`). То есть
половина скачанного медиа — мёртвый груз: пайплайн вместо него идёт в Pexels
и тратит квоту (200 запросов/час, 20000/мес) на то, что уже лежит на диске.
`assemble.py` эти файлы использует, `pipeline_smart.py` — нет.

**Что сделать.** `local_media(index) -> (kind, path)` рядом с `local_photo()`:
тот же поиск по номеру слота, но с приоритетом AI-фото > сток-видео >
сток-фото (ровно как `assemble.resolve_slot()` — логика уже написана и
проверена). В `main()` локальное видео уходит в тот же `video_render()`, что
и пексельское, — новой ветки рендера не нужно.

**Цена.** Только код, ~30 строк. Риска нет: путь `video_render()` уже
основной для стокового видео.

### 2.2. `assemble.py`: чанкование склейки

**Факт.** В `pipeline_smart.py` поймано вживую и исправлено: на цепочке из
150+ последовательных `xfade` в одном `filter_complex` ffmpeg возвращает код
0 (успех), но молча роняет кадры и застывает на кадре из середины ролика.
Лечение — чанки по 35 клипов (`xfade_chain_chunked`). В `assemble.py` этого
нет: там одна цепочка на все слоты. Проверку на застревание я добавил (теперь
ролик хотя бы не выйдет молча битым), но лечение — откат на голый `concat`,
то есть потеря ВСЕХ переходов сразу.

**Что сделать.** Перенести `_chunk_bounds`/`xfade_chain_chunked` из
`pipeline_smart.py` (обе функции уже готовы; в `assemble` границы чанков —
по смене хук/тело вместо смены секции).

**Цена.** Только код. Риска нет — механизм отработан на реальных эпизодах.

### 2.3. `assemble.py`: единый визуальный рецепт с основным сборщиком

**Факт.** `assemble.py` остался на первой версии грейда: `eq` + `vignette` +
плоский `noise`, CRF 23, 8 бит, центральный кроп. В `pipeline_smart.py` за то
же время появились: тон-кривая, selectivecolor, halation, deband, unsharp,
процедурное зерно-луп, авто-уровни/баланс белого по кадру, кроп по лицу/
салиенси, 10-битные промежуточные клипы, CRF 18 + финальный проход CRF 16,
явные метаданные Rec.709. То есть один и тот же эпизод, собранный по слотам
вместо пауз, выглядит заметно дешевле — при том что оба пути документированы
в ЧАСТИ 13 как равноправные.

**Что сделать.** Импортировать `film_look`/`grain_blend_complex`/
`compute_crop_offset`/`CLIP_PIX_ARGS`/`COLOR_META_ARGS` из `pipeline_smart`
вместо локальных копий (модуль уже импортируется другими скриптами; для
`assemble` нужен тот же guard на `__main__`, что я добавил в
`look_reference`).

**Цена.** Только код, но результат МЕНЯЕТ картинку слотового пути — значит
приёмка через реальный рендер и просмотр глазами (Шаг 7.5), а не «смёрджено
и забыто». Технического компромисса нет, но и «невидимой» правкой это не
назвать — поэтому отдельным пунктом.

### 2.4. Мемоизация дорогих измерений кадра

**Факт.** На каждого кандидата в `pexels_photo()` считаются: `ahash`,
`estimate_shot_size` (каскад Хаара), `clip_relevance` (CLIP), негативный
якорь (ещё один CLIP), доменные guard-промпты (два CLIP), `aesthetic_score`
(CLIP-эмбеддинг), `measure_luma`, `measure_levels`, `estimate_busyness`,
плюс `classify_domain` (8 текстовых промптов CLIP) и `look_correction_filter`
у победителя. Кандидатов до 20 на блок, блоков — сотни. Часть вызовов
дублируется на одном и том же файле (например, `estimate_shot_size` считается
и в `pexels_photo`, и в кэш-ветке, `measure_levels` — и для `pick_stat_variant`,
и для грейда).

**Что сделать.** Мемоизация по ключу `(путь, размер, mtime)` — не по одному
пути: файл кэша Pexels может быть перезаписан в рамках прогона (дубль-ветка),
и мемо по чистому пути соврал бы. Обёртка на 10 строк, применяется к
`ahash`/`estimate_busyness`/`estimate_shot_size`/`measure_levels`/
`measure_luma`/`clip_relevance`/`aesthetic_score`.

**Цена.** Только код. Результат бит-в-бит тот же (функции чистые), время
рендера — меньше; на CPU-инференсе CLIP это самая дорогая часть подбора.

### 2.5. Число рендер-воркеров на Windows считается только по ядрам

**Факт.** `_default_render_workers()` читает `/proc/meminfo` — то есть учёт
памяти работает на Linux/macOS и молча отключается на Windows (основная
платформа по ЧАСТИ 3). А каждый воркер держит холст 8000×4500 под `zoompan`:
на «много ядер + мало RAM» это честный OOM, от которого защита как раз и
писалась.

**Что сделать.** Кросс-платформенный замер: `ctypes` →
`GlobalMemoryStatusEx` на Windows (стандартный приём, без зависимостей), тот
же расчёт «~700МБ на воркера», тот же тихий откат на CPU-оценку при любом
сбое.

**Цена.** Только код, ~15 строк.

### 2.6. Коды возврата: «собрано с замечаниями» ≠ «не собрано»

**Факт.** `pipeline_smart.py` возвращает 1 и когда `final.mp4` НЕ собран
(жёсткий гейт), и когда собран, но QC нашёл похожие пары кадров. Из-за этого
`render_episode.py` пишет в `timeline_manifest.json` статус `failed` для
совершенно нормального рендера, а `render_with_retry.py` печатает «есть
замечания» там, где сборки не было вообще.

**Что сделать.** 0 — чисто; 2 — собрано, есть замечания (QC/пропуски при
`RENDER_STRICT_GATE=0`); 1 — не собрано. Обновить двух потребителей (там по
одной проверке).

**Цена.** Только код. Единственное требование — не забыть про
`render_with_retry.py`, который сегодня трактует любой положительный код как
«ретраить нечего» (это верно и останется верным).

### 2.7. Мультисток: осознанная реакция на 429/Retry-After

**Факт.** `try_sources()` ловит любое исключение и просто идёт к следующему
источнику. При исчерпании часовой квоты Pexels (200/час) это значит: 429 на
КАЖДОМ оставшемся слоте, полный перебор источников на каждом, +0.3с сна — и
всё это без единой попытки понять, что источник просто закрыт до конца часа.

**Что сделать.** На 429 (и на 403 с `X-Ratelimit-*`) — вывести источник из
ротации до конца прогона и сказать об этом одной строкой. Если сервер отдал
`Retry-After` и он меньше остатка работы — уважить его вместо отключения.

**Цена.** Только код. Побочный плюс: лог перестаёт быть простыней одинаковых
ошибок.

### 2.8. Дедуп между фото и видео

**Факт.** Визуальный дедуп (`used_photo_hashes`, aHash + hamming) работает
только для фото. Видео дедуплицируется исключительно по ID Pexels — то есть
сток-видео, визуально совпадающее с уже показанным фото (частый случай: одна
и та же студийная съёмка меча продаётся и кадром, и клипом), пройдёт как
новое. `qc_report()` в конце тоже смотрит только на фото.

**Что сделать.** Считать aHash по уже извлекаемому пробному кадру
(`extract_video_probe_frame()` вызывается для видео и так, ради проверки
релевантности) и складывать в тот же `used_photo_hashes`. Ноль новых
вычислений — кадр уже на диске в этот момент.

**Цена.** Только код, ~10 строк.

### 2.9. Сухой прогон тайминга перед платными шагами

**Факт.** Полный тайминг эпизода (блоки, длительности, запросы, план
переходов, титры/плашки) считается за секунды, а увидеть его можно только
запустив рендер целиком — часы CPU. `write_shot_manifest()` уже пишет почти
всё нужное, но вызывается внутри рендера.

**Что сделать.** Флаг `--plan-only`: посчитать блоки/длительности/запросы,
записать `shot_manifest.json`, `subtitles.srt`, `chapters.txt`, напечатать
свод (сумма длительностей против длины аудио, число sub-cuts, средний кадр
по секциям, слоты без темы) — и выйти. Ни одного вызова ffmpeg-рендера.

**Цена.** Только код. Прямо поддерживает дисциплину расходов из ЧАСТИ 1:
ошибку в тайминге видно до озвучки и до рендера.

### 2.10. CI: прогон тестов там, где есть ffmpeg

**Факт.** 152 теста из 573 требуют ffmpeg/torch/ruaccent и пропускаются в
любом окружении без них — включая дымовой тест полной сборки, то есть самый
ценный. Локально у пользователя ffmpeg есть, но прогон вручную никто не
гарантирует.

**Что сделать.** `.github/workflows/tests.yml`: `apt-get install ffmpeg`,
`pip install -r requirements.txt`, `pytest tests/ -q`. Опционально второй
job с `torch/transformers` (медленный, по расписанию, не на каждый пуш).

**Цена.** Бесплатные минуты GitHub Actions. Риска нет — CI ничего не
публикует и не трогает ключи (тесты сети не касаются).

## Как выбирать порядок

Пункты независимы. По соотношению «польза/риск» я бы шёл так:
**2.1** (мёртвое скачанное медиа + экономия квоты) → **2.4** (время рендера,
результат не меняется) → **2.10** (страховка от регрессий на будущее) →
**2.6**/**2.8**/**2.7** (мелкие, каждый по одной правке) → **2.5** (важно
именно на Windows) → **2.2** → **2.9** → **2.3** (последним: единственный
пункт, меняющий картинку и требующий приёмки глазами).
