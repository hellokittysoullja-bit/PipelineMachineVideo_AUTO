# AV ground-truth check

Создан 28 августа после реального случая: пользователь четыре раза подряд
писал идентичную жалобу на рассинхрон видео/фото с озвучкой. Каждый раз
Claude Code чинил реальный, но не главный баг и заявлял "исправлено",
опираясь на проверку, которая ничего не доказывала — субтитры сверялись
с картинкой, хотя субтитры считались той же сломанной функцией, что и
картинка. Настоящая причина (позиционная раздача авторских запросов без
связи со смыслом фразы + семь слоёв "оживления" тайминга, стирающих
позицию фразы) нашлась только когда проверка спустилась к сырым данным
(alignment.csv, text-text embedding-скорам) вместо повторной проверки уже
готовых производных.

## Правило 1: истина — только в первичных данных

Для КАЖДОГО типа утверждения — свой источник истины. Никогда не проверять
производную величину другой производной величиной того же механизма.

| Утверждение | НЕ доказательство | Источник истины |
|---|---|---|
| "Кадр X начинается в момент фразы Y" | `subtitles.srt` (считается тем же оценочным `block_durations()`, что и сам монтаж) | `media_plan/phrase_timeline.json` (`load_alignment_onsets()` + `hook_visual_starts()`, реальный alignment + реальное сжатие кроссфейдом) |
| "Тайминги в порядке" | наивный `cumsum(durations)` | `hook_visual_starts()` / `phrase_timeline.json["blocks"][i]["drift_sec"]` |
| "Картинка/видео подходит по смыслу" | "визуально похоже", отчёт `relevance_gate_report.json` (проверяет только запрос-кандидат, не текст-блок) | `media_plan/director_relevance_report.json` ИЛИ прямой вызов `visual_director.sentence_relevance(path, sem_text)`/`text_text_similarity()` |
| "Кадр резкий" | "выглядит нормально на скриншоте 320px" | `image_sharpness_score()`/`video_sharpness_ok()` на РЕАЛЬНОМ кадре из готового `final.mp4`, не на исходнике |
| "Готовый рендер соответствует жалобе пользователя" | код читается и "по логике должен работать" | реально пересчитать нужную величину на РЕАЛЬНОМ script.txt/audio этого эпизода и посмотреть число |

Если источника истины для конкретного утверждения не существует (нет
alignment, нет phrase_timeline.json с `locked: true`) — сказать это прямо
пользователю, а не подставить производную оценку и выдать её за проверку.

## Правило 2: назвать вслух, что именно проверяет каждый отчёт

Перед "отчёты чистые" — явно сопоставить каждый пункт жалобы пользователя
с конкретным отчётом/проверкой, которая его закрывает. Если для пункта
жалобы отчёта нет — это не "наверное всё хорошо", это дыра в проверке,
которую нужно закрыть измерением, а не предположением.

Отчёты этого пайплайна и их ось (НЕ взаимозаменяемы):
- `relevance_gate_report.json` — кандидат против СВОЕГО запроса (не против
  текста блока, не про тайминг).
- `director_relevance_report.json` — победитель против РЕАЛЬНОГО текста
  блока (не про тайминг, не про резкость).
- `render_qc_report.json` — резкость готового рендера против источника
  (не про смысл, не про тайминг).
- `phrase_timeline.json` — только тайминг (не про смысл, не про резкость).
- `stock_exhausted_report.json` — строго более сильный сигнал, чем
  relevance_gate_report.json: не "победитель не идеален", а "ни один
  кандидат из ВСЕГО просмотренного пула не прошёл ни relevance, ни
  резкость" (независимо от дедупа). Вывод для этих слотов другой — не
  "сверить глазами на Шаге 7.5", а "сгенерировать AI-картинку/видео на
  Шаге 5, стоку тут физически нечего предложить".
- Ни один из них не заменяет остальные и не заменяет визуальный проход
  Шага 7.5 (тонкая контекстная нерелевантность/эстетика — не формализуемы).

## Правило 3: второй одинаковый симптом = модель причины неверна

Если пользователь второй раз описывает СИМПТОМ, который уже "исправлен" —
запрещено объяснять фикс подробнее или переспрашивать "а видел ли ты новый
файл". Вместо этого:
1. Остановиться и явно сформулировать: "какую конкретно причину я предполагал,
   и каким измерением я это подтвердил?" — если измерения не было (была
   только логика "должно помочь"), это и есть дыра.
2. Спуститься на уровень ниже к более сырым данным, чем в прошлый раз:
   код → готовый кадр/цифра → сырой alignment/embedding-скор.
3. Перечитать код, который уже читался раньше в ЭТОЙ ЖЕ сессии по другому
   поводу, специально держа в уме именно эту жалобу — реальная причина в
   этом случае лежала в коде (`resolve_queries()`, `apply_human_jitter()`
   и соседние функции), прочитанном несколькими ходами раньше без вопроса
   "а это вообще связано со смыслом/позицией фразы?".
4. Прямое наблюдение пользователя (посмотрел готовое видео) — источник
   истины не слабее кода. При конфликте "я проверил, там всё ок" против
   "пользователь смотрит и видит не то" — предполагать неправым метод
   проверки, не человека.

## Как использовать (чек-лист перед ответом "работает"/"проверено")

1. Дождаться реального рендера (не полагаться на статический разбор кода
   без факта запуска).
2. Прочитать `media_plan/phrase_timeline.json` — `locked`, `worst_drift_sec`
   против `max_allowed_drift_sec`. Не привязан — сказать это прямо.
3. Прочитать все report-файлы из Правила 2, сопоставить с пунктами
   жалобы пользователя поимённо.
4. На спорных/ранее жаловавшихся слотах — вытащить реальный кадр из
   готового `final.mp4` в нужную секунду (`ffmpeg -ss <онсет_из_phrase_timeline> -i final.mp4 -vframes 1 ...`)
   и посмотреть глазами, что там ФАКТИЧЕСКИ показано в момент реальной фразы.
5. Только после 1-4 — формулировать ответ пользователю, явно указывая, что
   именно измерено (числа, не "должно быть лучше").
